# Kirton Compiler 1.2 — этап 5

## Архитектура модулей и вызовов

Bytecode VM остаётся отдельным режимом запуска (`--bytecode`). AST-интерпретатор
сохраняет роль эталона. Импортируемый исходный файл разбирается существующим
`parse_program`, после чего его функции и верхнеуровневые операторы компилируются
и выполняются той же VM. Включаемый файл использует текущее окружение, как в AST.
Перехода к `vm_import` или `eval_program` из байткодового режима нет.

Загрузчик повторно использует `kir_resolve_module_path`,
`kir_normalize_module_key`, `kir_module_name_from_path` и `kir_read_text_file` из
интерпретатора. Кэш живёт только в рамках одного запуска VM и индексируется
нормализованным путём. Загрузка помечается до исполнения инициализации, поэтому
цикл обнаруживается тем же способом, что и в AST. Повторный импорт использует
готовые экспорты и не запускает инициализацию снова.

Каждый пользовательский модуль имеет отдельное окружение без родительского
окружения импортёра. В его экспортный словарь попадают только функции верхнего
уровня, как в AST. Функции хранят замыкание на окружение модуля. Окружения,
экспорты и константы модульного байткода отмечаются корнями существующего GC;
новый сборщик не вводился. Ошибка импорта распространяется через текущий
обработчик исключения VM, в том числе при цикле и ошибке разбора.

## Встроенные функции

Операции стандартной библиотеки не копируются: VM вызывает зарегистрированный
`KirNativeFn`. Внутренняя таблица native-слотов помечает callbacks, которые
допущены в Bytecode.

| Native API | Доступ в Kirton | Bytecode |
| --- | --- | --- |
| list, dict, str | Существующие глобальные функции | Поддержаны безопасные регистрации |
| math, JSON, regex, path | Существующие глобальные функции | Поддержаны безопасные регистрации |
| math3d | Импортируемое пространство имён | Поддержано |
| fs, OS, process, HTTP, timers, memory/resources, graphics, FFI | Модульные функции и/или ресурсы среды | Не поддержаны |

Другие зарегистрированные native-модули отклоняются на этапе компиляции, если
для их имени не найден пользовательский файл. Это оставляет за пределами этапа
файловые и системные дескрипторы, сокеты, ручную память, графику и FFI.

Аргументы нативного вызова остаются на стеке VM во время callback. Если callback
добавил диагностику, VM сохраняет исходные сообщение и координаты как ошибку,
которую может перехватить `попробовать`.

## Исключения и диагностика

`попробовать`, `перехватить` и `всегда` исполняются вложенными байткодовыми
фрагментами. Исключение несёт словарь с полями `код`, `сообщение`, `файл`,
`строка`, `столбец` и `стек`. Объект ошибки и стек вызовов удерживаются корнями
до завершения `finally`. Приоритет ошибки или управляющего перехода в `finally`
совпадает с текущим AST-контрактом; регрессионные тесты охватывают возврат,
продолжение, прерывание и замену ошибки.

Чтение исходника модуля обрабатывает отказ выделения буфера как ошибку чтения;
этот путь проверяется allocator-failure тестом. Внутренние выделения парсера
по-прежнему используют общие аварийные allocators проекта, поэтому полное
восстановление из OOM внутри построения AST остаётся ограничением.

Общий кэш исходников теперь инициализирует индекс пустой строки после
завершающего перевода строки. Это устраняет чтение неинициализированного
смещения при диагностике синтаксической ошибки последней строки файла.

## Покрытие этапа

| Возможность | Статус |
| --- | --- |
| Пользовательские импорты, алиасы, повторный импорт | Реализовано |
| Разрешение путей и кэш на время жизни VM | Реализовано с общими helper-функциями |
| Функции и замыкания между модулями | Реализовано |
| Вложенный импорт и обнаружение циклов | Реализовано |
| `включить` в текущее окружение | Реализовано |
| Основные глобальные native callbacks | Реализовано для явно безопасных регистраций |
| Нативный модуль `math3d` | Реализовано |
| Исключения, `finally`, native/module errors | Реализовано в проверенных сценариях |
| FFI, память/ресурсы, файловый I/O, сеть, графика | Не поддерживается |
| Не реализованные ранее конструкции AST | Диагностика компилятора, без fallback |

Сериализация байткода, публичный SDK и синтаксис не менялись. Время разбора и
компиляции импортируемых модулей добавляется к `compile_ms`; `execute_ms`
исключает измеренное динамическое время компиляции.

## Release-замеры

MSVC Release, одинаковые программы, 9 запусков каждого режима, медиана.
Парсинг основной программы исключён. Для Bytecode `compile_ms` включает
разбор/компиляцию импортируемых модулей; `execute_ms` не включает эти замеренные
этапы. AST разбирает модули во время исполнения, поэтому его время включает их
разбор. Результаты AST и Bytecode проверены на совпадение в каждом сценарии.

| Сценарий | AST исполнение, мс | Bytecode compile, мс | Bytecode исполнение, мс | Bytecode всего, мс |
| --- | ---: | ---: | ---: | ---: |
| Первый импорт | 0.069 | 0.031 | 0.054 | 0.085 |
| Повторный импорт | 0.108 | 0.056 | 0.081 | 0.137 |
| 10 тыс. вызовов импортированной функции | 2.843 | 0.033 | 1.998 | 2.031 |
| 10 тыс. вызовов через второй модуль | 4.631 | 0.064 | 2.748 | 2.812 |
| 10 тыс. native-вызовов (`корень`) | 1.790 | 0.001 | 2.863 | 2.864 |
| 1 тыс. перехваченных ошибок | 2.029 | 0.002 | 1.453 | 1.455 |

Измерения показывают ускорение циклов с пользовательскими импортированными
функциями и исключениями в этих конкретных сценариях, но native-вызов и полная
стоимость первого/повторного импорта медленнее. Эти числа зависят от окружения и
не являются общей гарантией производительности Bytecode VM.
