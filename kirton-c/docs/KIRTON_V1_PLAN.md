# Киртон: план полной языковой основы

## Цель

Киртон — самостоятельный язык общего назначения с простым русским синтаксисом. Программист, знающий русский, должен иметь возможность читать и писать обычные программы без изучения Python-синтаксиса. Язык должен подходить и для системных задач: после стабилизации основы к нему должно быть возможно подключать большие C-библиотеки, включая Vulkan, через общий механизм расширения.

Скорость относительно Python пока не доказана измерениями. Её нужно оценивать на сопоставимых задачах после фиксации семантики, затем улучшать реализацию без изменения контракта языка.

## Границы и принципы

- Поддерживаемая реализация — `kirton-c`. Python-версия была экспериментом и не является второй реализацией языка.
- Bare-metal ядро KirtonOS — отдельный проект.
- Язык и конкретные библиотеки — разные слои. Оконные, графические и прочие нативные функции полезны как биндинги, но не определяют полноту языка.
- Новые платформенные функции не приоритетны, пока не определены семантика языка, управление памятью, модули и общий интерфейс для внешнего кода.
- Цель системной интеграции — общий интерфейс расширения, чтобы добавление Vulkan или иной библиотеки не требовало изменений грамматики и ядра Киртона для каждой функции.

## Дорожная карта

### Этап 0. Устранить подтверждённые ошибки — выполнен

- Исправлен разбор смешанных приоритетов операторов.
- Добавлены проверки синтаксических ошибок, неизвестных переменных и числа аргументов; выполнение останавливается после ошибки и возвращается ненулевой код.
- Исправлены сравнение коллекций, лексическая область псевдонимов и время жизни имени файла в AST.
- Добавлены целые произвольной точности, точная арифметика `+`, `-`, `*`, сравнения и поддержка больших целых в JSON.
- Исправлены русские канонические слова, строковые escape-последовательности и значение `пусто`.
- Поправки платформенных функций и legacy 2D уже сделаны как сопутствующее исправление дефектов; расширять эти наборы сейчас не нужно.
- Последняя проверка основной конфигурации: 25/25.

### Этап 1. Завершить спецификацию ядра языка — выполнен для Kirton 1.0

Зафиксировать поведение до расширения библиотек:

- **Числа:** точные целые и вещественные, деление, целочисленное деление и остаток, переполнение, преобразования, сравнения, побитовые операции и сдвиги. Побитовые операции и фиксированные ширины важны для системных API и битовых флагов.
- **Переменные и функции:** области видимости, изменение значений, замыкания, точное число/порядок аргументов, аргументы по умолчанию, именованные и переменные аргументы.
- **Управление потоком:** `вернуть`, `прервать`, `продолжить`, циклы и гарантированные правила выхода.
- **Типы и данные:** список, словарь, строки, записи/структуры, перечисления, неизменяемые значения и представление внешних/непрозрачных дескрипторов. Решить, нужны ли классы для ядра или достаточно записей и функций.
- **Ошибки:** единая модель диагностики и обработки ошибок, включая ошибки внешних функций; решить, нужны ли исключения или явные результаты.
- **Модули:** явные экспорты, импорты, алиасы и детерминированное разрешение одинаковых имён из разных модулей.
- **Память:** время жизни коллекций, строк и больших целых; безопасное владение памятью при вызове внешнего C-кода.

Результат этапа — разделы `docs/SYNTAX_V1.md` с ответами на эти вопросы и короткими программами, подтверждающими правила.

### Этап 2. Реализовать и проверить контракт — выполнен для Windows x64/MSVC

- Закрыть только те изменения парсера, VM и значений, которые нужны утверждённой спецификации.
- Убрать утечку больших целых в долгоживущих процессах и разрешить конфликты функций из импортированных модулей.
- Завершить исходные позиции ошибок, включая импорты и публичный API.
- Создать conformance-тесты: каждый пункт спецификации должен иметь позитивную проверку, ошибочные случаи — негативную.
- Проверить учебные программы и небольшое приложение, написанные только на Киртоне.

### Этап 3. Зафиксировать языковую основу 1.0 — выполнен

- Заморозить грамматику, семантику значений, функции, ошибки, импорты, CLI и публичный интерфейс расширений.
- Оптимизация реализации допустима, если conformance-набор подтверждает прежний результат.
- Не считать отдельные окна, графику или Vulkan частью грамматики языка.

### Этап 4. Сделать общий интерфейс внешнего кода

Спроектировать и реализовать системный слой расширения, пригодный не для одной библиотеки:

- подключение внешних библиотек и вызов функций по C ABI;
- точные C-типы фиксированной ширины, указатели и непрозрачные дескрипторы;
- описание структур, перечислений, объединений и массивов с проверяемой раскладкой;
- правила владения и освобождения памяти;
- обработка кодов ошибок и обратных вызовов;
- тестовая C-библиотека для проверки ABI, размеров, выравнивания и времени жизни данных.

Конкретные биндинги живут отдельными модулями или генерируются по описанию API; ядро языка не получает специальные функции для каждой библиотеки.

### Этап 5. Проверить системные возможности на Vulkan

Использовать Vulkan как крупную интеграционную проверку общего интерфейса: загрузить библиотеку, создать instance/device, управлять структурами и дескрипторами, выполнить минимальный рендеринг. Сначала доказать работу общей модели C-вызовов, потом наращивать покрытие Vulkan.

### Этап 6. Измерить и развивать скорость и инструменты

- Снять воспроизводимые замеры времени и памяти против Python на одинаковых задачах.
- Отдельно измерить арифметику, коллекции, строки, вызовы функций и внешние вызовы.
- Выбрать оптимизацию по результатам замеров; сохранять conformance-проверки.
- После стабилизации развивать REPL, форматтер, документацию, поддержку редакторов и пакетную систему.

## История стабилизации

Записи ниже описывают последовательные этапы работ и сохраняют исторические
статусы на момент каждой записи. Актуальный статус выпуска указан в конце этого
раздела и в [`RELEASE_GATE_V1.md`](RELEASE_GATE_V1.md).

Этап 0 (аудит) выполнен как статическая проверка исходников, CMake/тестовых
сценариев и документации. Тесты и сборка в рамках этого аудита не запускались.
Подтверждённые приоритеты: корректная семантика локального `пусть`, устранение
глобального fallback при разрешении функций модулей, обработка runtime-ошибок,
пользовательские типы и проверка загрузчика BMP/обработки ошибок выделения
памяти.

Текущий этап — проектирование контракта языка. [SYNTAX_V1.md](SYNTAX_V1.md)
переработан как проект спецификации: он предлагает правила затенения, замыканий,
модулей, ошибок, структур и перечислений. На тот момент документ ещё не был
заморожен. Добавлена
[матрица conformance](CONFORMANCE_V1.md), которая отделяет текущее покрытие от
новых тестов, нужных для проверки контракта.

Память и FFI не расширяются на этом этапе. В текущем коде есть отдельные кучи
значений и больших целых с GC-интеграцией, арены, нативные ресурсы и FFI V1/V2.
До 1.0 требуется проверить их взаимодействие с замыканиями, долгую работу,
старые нативные модули и поддерживаемые платформы. Исторические README и
документы памяти содержат устаревшие статусы; их нужно согласовать с текущей
реализацией при последующей документальной стабилизации.

Первый семантический контракт — различие объявления `пусть` и присваивания `=` —
внесён в `src/eval.c`; добавлены сценарии затенения, присваивания во внешнее
окружение и ошибки неизвестного имени. MSVC/Windows build прошёл, полный CTest
набор прошёл 66/66.

Вложенные функции и возвращаемые замыкания реализованы как GC-управляемые
значения с удержанием захваченного окружения. Проверены изменяемый захват,
доступ после выхода из кадра, hoisting mutual recursion и вызовы через несколько
сборок GC; `kirton_closures` включён в CTest.

Полный набор подтверждён последовательным прогоном: MSVC/Windows build и 67/67
CTest passed.

Глобальный fallback при разрешении имён модулей удалён. Импортированные функции
вызываются через namespace; одноимённые функции двух модулей проверены текущим
тестом области видимости. Старый пример core smoke переведён на квалифицированный
вызов. Сборка MSVC/Windows прошла, полный последовательный CTest — 68/68.

Runtime-обработка ошибок реализована: ближайший `перехватить` получает значение
с кодом, сообщением, координатами и стеком; `всегда` выполняется при ошибке,
обычном выходе и `вернуть`. Перехваченные ошибки не печатаются. Проверены
вложенный catch, продолжение выполнения, unhandled cleanup и ненулевой код
завершения. MSVC/Windows build прошёл, полный последовательный CTest — 70/70.

Пользовательские структуры и перечисления реализованы как GC-управляемые
значения. Проверены именованные конструкторы, доступ/изменение с проверкой
типов, варианты перечислений, неверные/пропущенные поля, GC-нагрузка и
межмодульное использование через функции/замыкания. Ключевое слово `структура`
остаётся доступным как имя атрибута после точки для совместимости с
`память.структура`.

Memory-аудит закрыл переполнения размеров BMP, ограничил размер bitmap allocation,
добавил защиту глубины JSON и безопасный рост буфера regex с проверкой пределов.
Проверки включают malformed BMP, чрезмерную JSON-вложенность, JSON NaN/Inf,
deterministic native-input smoke и regex-замену. Добавлены task tracker и expense
report как многофайловые приложения; строковая индексация по Unicode-кодпоинтам
реализована. Аудит старых native modules записан в
[`NATIVE_RESOURCE_AUDIT.md`](NATIVE_RESOURCE_AUDIT.md): process-exit cleanup есть,
но модули остаются process-global и не изолированы по VM.

Сборка MSVC/Windows и полный последовательный CTest прошли 125/125 в Debug и
Release; полный CTest под MSVC AddressSanitizer также прошёл 125/125. Отдельная production Release
сборка с `BUILD_TESTING=OFF` прошла, то есть allocator fault hooks исключаются
из сборки без тестов.

Установка и первый запуск описаны в `docs/GETTING_STARTED_V1.md`; CMake install
проверен, установленные task tracker и expense report запущены успешно.

До заморозки остаются OOM injection в остальных native modules, coverage-guided
запуск libFuzzer (Clang в окружении отсутствует), ручные graphics/audio
сценарии, реальные GPU/async драйверы и запись точной версии/архитектуры Linux
GCC. Legacy graphics/audio теперь имеют process-exit cleanup, но их process-global
состояние не изолировано между VM; спецификация ограничивает их одной VM на
процесс. На момент этой записи спецификация ещё не была заморожена.

## Актуальный статус

Контракт Kirton 1.0 заморожен в [`SYNTAX_V1.md`](SYNTAX_V1.md). Обязательная
матрица сопоставлена с CTest; Windows x64/MSVC прошёл Release gate 126/126,
production Release install и smoke двух установленных многофайловых приложений.
Linux, coverage-guided fuzzing и реальные GUI/GPU/audio устройства явно не
заявлены как пройденные. Оставшиеся работы и их релизная классификация ограничены
таблицей в [`RELEASE_GATE_V1.md`](RELEASE_GATE_V1.md); аудит после её закрытия не
расширяется без подтверждённого blocker.
