# Kirton Memory System V2.5 — управляемые внешние ресурсы

**Статус:** экспериментальный слой владения нативными ресурсами (C11), поверх GC и Memory V2.0–V2.4. Это **не** универсальный FFI, не ABI с динамической загрузкой, не многопоточный runtime и не компилятор.

## Зачем это нужно

GC освобождает строки и коллекции Kirton, но системные объекты (файлы, сокеты, GPU-дескрипторы, контексты библиотек) требуют собственных функций закрытия. Поэтому V2.5 вводит `VAL_NATIVE_RESOURCE`: непрозрачное значение, принадлежащее конкретной VM, с **одной функцией освобождения** (destructor) и явным жизненным циклом.

У него нет открытого адреса в скрипте. Вызов нативного кода с доступом к адресу возможен только через синхронное C API. Скрипт, получивший такой ресурс от хоста или нативного модуля, может проверить его состояние и закрыть.

## Публичный C API

Из `include/kirton/eval.h`:

```c
typedef void (*KirNativeResourceDestroy)(void* handle, void* user_data);
typedef int (*KirNativeResourceVisit)(void* handle, void* user_data);

Value vm_native_resource_adopt(VM* vm, void* handle, const char* type_tag,
                               KirNativeResourceDestroy destroy, void* user_data);
int vm_native_resource_is_open(VM* vm, Value resource, const char* type_tag);
int vm_native_resource_close(VM* vm, Value resource);
int vm_native_resource_visit(VM* vm, Value resource, const char* type_tag,
                             KirNativeResourceVisit visitor, void* user_data);
```

- `adopt` **передаёт владение при успехе** (`VAL_NATIVE_RESOURCE`). При `VAL_NIL` владение остаётся у вызывающей стороны. Обязательны ненулевой дескриптор, непустой идентификатор типа и функция освобождения. `type_tag` копируется.
- `is_open` проверяет принадлежность VM, идентичность дескриптора, незакрытое состояние и (если указан) точный `type_tag`.
- `close` вызывает `destroy` **ровно один раз**; повторное закрытие и закрытие в момент активного визита отклоняются (`0`). Прочие ссылки после закрытия остаются дескрипторами *закрытого* ресурса.
- `visit` временно удерживает GC-корень и передаёт `handle` **только на время синхронного C-вызова**. Проверяется тип. Внутри визита `close` и `vm_try_free()` отклоняются. GC можно запустить — значение останется живым. Возвращается результат callback (0 также означает невозможность выполнить визит).
- Невостребованный ресурс вызывается `destroy` при сборке мусора. Не закрытый к концу VM ресурс вызывается `destroy` при `vm_try_free()`/`vm_free()` (при условии отсутствия активных визитов/borrow).
- `vm_value_pin()`/`vm_value_unpin()` нужны, если внешний C-код держит **Value** между сборками GC. Просто копирование `Value` в C-структуру **не** создаёт GC-корень. При передаче в функцию Kirton аргументы становятся временными корнями.

### Пример: хост передаёт файловый дескриптор

```c
#include "kirton/eval.h"
#include <stdio.h>

static void close_file(void* handle, void* ignored) {
    (void)ignored;
    fclose((FILE*)handle);
}

static int inspect_file(void* handle, void* ignored) {
    (void)ignored;
    return ferror((FILE*)handle) == 0;
}

/* vm уже создана; file нужно открыть ДО adopt. */
FILE* file = fopen("report.txt", "rb");
if (file) {
    Value resource = vm_native_resource_adopt(vm, file, "std.FILE", close_file, NULL);
    if (resource.kind != VAL_NATIVE_RESOURCE) fclose(file); /* adoption failed */
    else {
        KirPinnedValue* pinned = vm_value_pin(vm, resource);
        if (pinned) {
            (void)vm_native_resource_visit(vm, resource, "std.FILE", inspect_file, NULL);
            (void)vm_native_resource_close(vm, resource);
            vm_value_unpin(vm, pinned);
        }
    }
}
```

Пример — **фрагмент C-кода хоста**, а не команда Kirton. `vm` должна существовать, подключается `kirton_core`. Для файлов, сокетов или GPU-объектов нужно использовать соответствующую платформенную функцию освобождения.

## Доступ из Kirton

Новый встроенный модуль `ресурсы` экспортирует `открыт` и `закрыть`.

```text
импорт ресурсы

функция обработать_полученный_ресурс(ресурс)
    если ресурсы.открыт(ресурс) то
        печатать("Ресурс ещё используется")
        ресурсы.закрыть(ресурс)
    конец
конец
```

Обычная программа **не может создать произвольный нативный указатель**. Ресурс выдаёт хост/нативная библиотека, которая обязана гарантировать срок жизни переданного объекта. Метод `тип(значение)` возвращает `"внешний_ресурс"`. Сериализация в JSON запрещена, в том числе для вложенных ресурсов.

## Реализованные меры безопасности

1. **VM-изоляция:** чужой ресурс отклоняется при прямом C API, `pin` и передаче аргументов функции Kirton, даже если он находится внутри списка/словаря.
2. **Уникальная идентичность:** каждый ресурс получает не повторяющийся в процессе числовой ID. Копия старого `Value` не может стать валидной лишь потому, что аллокатор переиспользовал тот же адрес дескриптора (ABA).
3. **Exactly-once destruction:** явное закрытие, GC и освобождение VM вызывают `destroy` не более одного раза. Дескрипторы-заглушки могут пережить закрытие, но не владеют внешней памятью.
4. **Корневание во время визита:** даже принудительный GC не удалит посещаемый ресурс; VM не может закрыться при активном визите.
5. **Защита от повторного входа:** C API для работы с ресурсами, создание корней, выполнение программ и запуск GC отклоняются во время native destructor callback. Другие формы повторного входа запрещены контрактом.
6. **Очистка при release_all:** `v_value_heap_release_all()` завершает нативные ресурсы, даже когда отдаёт владение обычными значениями из кучи.
7. **Сохранение прежнего API:** арены, записи и типизированные массивы работают как в V2.4.

## Известные ограничения

- **Только однопоточное синхронное исполнение.** Показатели занятости и счётчик ID не являются атомарными. Не используйте ресурс одновременно с разных потоков.
- **Запрещено сохранять указатель из `visit` после возврата callback.** Kirton не контролирует ошибочный C-код, способный скопировать адрес. Для асинхронного I/O, DMA или Vulkan нужны отдельные правила завершения операций и ожидания сигналов.
- **Native destructor не должен вызывать Kirton API**, менять хранилище VM, делать `longjmp` или передавать исключения C++ через C. Допускается освобождение самого внешнего ресурса.
- **Нет автоматической трассировки указателей в нативном дескрипторе**. Если нативная библиотека хранит `Value`, он должен быть закреплён отдельным `vm_value_pin`; иначе GC вправе удалить объект.
- **Нет обобщённого FFI, runtime-загрузчика, динамических библиотек, varargs, ABI-структур, пользовательских native callbacks из скрипта**. Cleanup callback и синхронный C visitor — это пока не произвольные обратные вызовы в Kirton.
- **Нативный дескриптор не обязан быть `malloc`-указателем** — это может быть непрозрачный указатель на внешний объект. Целочисленные OS `HANDLE` требуют корректной адаптации к `void*` и платформенного release callback.
- **Не реализована полная модель заимствования между обычными GC-объектами и произвольной нативной памятью**, равно как и безопасный режим потокового удержания GPU-ресурсов.
- **Windows/MSVC не проверены**; проведён Linux GCC build и санитайзеры.

## Проверки

Новый тест `tests/memory_v2_resource_api.c` проверяет: ручное закрытие из Kirton и C, ошибки аргументов и типа, изоляцию VM, хранение в списке через вызов функции, удержание через pin, принудительный GC во время визита, запрет закрытия и уничтожения VM при активном визите, автоматическую финализацию GC и VM, сериализацию JSON, повторное закрытие, некорректный ID и 1200 короткоживущих объектов. Дополнительно проверяется `v_value_heap_release_all()`.

Испытания текущего исходного состояния: **57/57 Release**, **57/57 ASan + UBSan + LeakSanitizer** на Linux. Это подтверждает покрытие проверенных сценариев, но не абсолютную корректность всей системы памяти или готовность к Kirton 1.0.

## Дальнейший порядок работ

1. Проверить MSVC/Windows и стабильность ABI структур `Value`.
2. Проектировать отдельные синхронные и асинхронные handle-контракты для C ABI/FFI. Завершение GPU/IO-операции должно быть явной частью времени жизни.
3. Добавить типизированные handle-обёртки для реальных системных объектов и интеграционные тесты, затем общий загрузчик библиотек/FFI.
4. Продолжить аудит ошибок GC в остальных нативных модулях — особенно статические globals с `Value` и регистрация корней.
