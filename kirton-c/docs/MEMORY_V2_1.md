# Kirton Memory System V2.1 — типизированные массивы (экспериментальный этап)

Дата: 2026-11-03. Это продолжение `MEMORY_V2.md` и **не окончательная спецификация Kirton 1.0**.

## Цель и границы

Программист может явно зарезервировать область памяти и хранить в ней непрерывные числовые массивы без создания отдельного `Value` на каждый элемент. Обычные списки, словари и строки по-прежнему управляются GC. Дескриптор массива управляется GC и удерживает родительскую арену достижимой, но **сброс/закрытие области вручную делает все её старые массивы недействительными**.

Пример:

```kirton
импорт память

пусть область = память.создать(4096)
пусть координаты = память.массив(область, "число64", 100)
координаты[0] = 12.5
координаты[1] = -8.25
печатать(координаты[0])
печатать(память.длина_массива(координаты))

для каждого значение в координаты
    // здесь можно обработать значение
конец

память.сбросить(область)
печатать(память.действителен_массив(координаты)) // ложь
память.закрыть(область)
```

Поддерживаются четыре типа элементов:

| Имя | Хранение | Значения |
|---|---|---|
| `байт` | `uint8_t` (1 байт) | 0…255 |
| `целое32` | `int32_t` (4 байта) | −2^31…2^31−1 |
| `целое64` | `int64_t` (8 байт) | −2^63…2^63−1 |
| `число64` | IEEE 754 `double` (8 байт) | конечные числа, включая дробные |

`целое64` сохраняет точные целые, в том числе больше 2^53, если исходное число Kirton было точным целым. `число64` сохраняет значение в представлении `double`: большие целые могут округляться при преобразовании, а бесконечности и NaN запрещены при записи. Порядок байтов — **нативный** для хоста; это не сериализуемый бинарный формат.

Дополнительные функции модуля `память`:

| Вызов | Результат |
|---|---|
| `массив(область, "целое32", количество)` | новый нулевой массив нужного типа |
| `длина_массива(массив)` | длина по элементам |
| `тип_массива(массив)` | русское имя типа элемента |
| `действителен_массив(массив)` | истина / ложь |
| `взять(массив, индекс)` | прочитать элемент |
| `положить(массив, индекс, число)` | записать число; истина при успехе |

Сокращения: `массив[индекс]` и `массив[индекс] = значение`. Поддерживается `для каждого ... в массив`.

## Безопасность и контракт владения

- При создании проверяются вместимость области, переполнение `count * sizeof(element)` и выравнивание. Массивы выделяются целиком из арены; при нехватке памяти возвращается ошибка, а не частичный массив.
- Все элементы обнуляются при выделении и повторном выделении после сброса.
- Чтение/запись проверяют длину, тип значения и поколение области. Неверная попытка **не приводит к чтению или записи памяти**.
- Копирование `Value` массива создаёт ещё одну ссылку на тот же дескриптор, а не отдельный буфер. Списки и словари могут содержать ссылки на массивы.
- GC просматривает ссылки на массивы из списков/словарей и помечает их родительскую область. Достижимый массив предотвращает *автоматическое* освобождение области, но не запрещает явный `сбросить` / `закрыть`.
- При передаче через C API все удерживаемые между вызовами значения необходимо закреплять `vm_value_pin` / `vm_value_unpin`. Проверка чужих memory handles рекурсивно проверяет вложенные списки и словари с защитой от циклов. Это не делает любой произвольный указатель C безопасным.
- `json.написать` отклоняет дескрипторы массивов: их нельзя автоматически сериализовать.
- Для обычной работы с объектами Kirton используйте стандартные списки; в аренах пока допустимы **только числовые типы, без ссылок на VM-объекты**. Это сознательное ограничение, предотвращающее скрытые GC-корни в сырой памяти.

## Тестирование

В базовом наборе появился C-тест точности 32/64-битных чисел, выравнивания, переполнений, циклических контейнеров, изоляции VM, pin/unpin и GC, тест сценария языка и отрицательные проверки использования устаревших буферов/неверных типов/индексов/JSON. Нагрузочный тест 250 раз выделяет и инвалидирует массив на 1 000 000 элементов `целое64` внутри одной области 8 МБ, проверяя корректность повторного использования и очистку дескрипторов.

Запуск:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Санитайзеры: `-fsanitize=address,undefined -fno-omit-frame-pointer`, `ASAN_OPTIONS=detect_leaks=1`, `UBSAN_OPTIONS=halt_on_error=1` на Linux/GCC. Отдельный Windows/MSVC прогон пока не выполнен.

## Чего в этом этапе нет

1. Типизированных записей/структур и массивов ссылочных объектов, автоматического вывода размеров структур или произвольной раскладки полей.
2. Полноценного **владения** на уровне синтаксиса, compile-time borrow checking, вложенных заимствований.
3. Сырых указателей, FFI, обратных вызовов, явно опасного блока `небезопасно`, Vulkan.
4. Параллельного GC, детерминированных финализаторов и гарантированных коротких пауз сборщика.
5. Лимита общего потребления RAM VM: имеющийся лимит охватывает лишь payload открытых арен (не метаданные/AST/BigInt/сторонние библиотеки).
6. Надёжного продолжения исполнения после runtime-ошибки: механизм catch/обработки ошибок языка ещё не реализован.
7. Гарантий нативной производительности для прохода по массиву в AST-интерпретаторе: компактное хранение не устраняет интерпретационные накладные расходы каждого доступа.

Следующий логичный этап: спецификация безопасных **записей с фиксированной раскладкой**, модели заимствования между GC и аренами, контрактов C ABI. Прежде чем предоставлять сырые указатели, нужно определить явное владение и управление временем жизни нативных ресурсов.
