# Kirton Memory System V2 — первая рабочая часть (PREVIEW)

Дата: 2026-11-03. **Это НЕ завершённая Memory System V2 и НЕ замороженная спецификация Kirton 1.0.**

## 1. Две модели одновременно

- По умолчанию обычные строки, списки, словари и большие целые продолжают жить в отслеживаемых кучах VM и освобождаться трассирующим GC.
- По явному запросу программист создаёт фиксированную **область памяти** и размещает в ней **байтовые буферы**. Разработчик выбирает момент сброса или закрытия области.
- Объекты-дескрипторы «область» и «буфер» *по-прежнему принадлежат GC*. Явно контролируется backing storage, а не время жизни всех объектов VM. Буфер удерживает в графе достижимости родительскую область; сборщик обходит эту связь.
- Абсолютный/физический адрес выделения не выбирается. ОС выделяет виртуальную память; размещение контролируется логической областью и выравниванием.

## 2. Работающий синтаксис

```kirton
импорт память

// Область с 4096 байт полезной ёмкости; базовое выравнивание 64 байта.
пусть область = память.создать(4096)

// 32 байта, начало выровнено на 16 байт по РЕАЛЬНОМУ адресу.
пусть буфер = память.выделить(область, 32, 16)
память.записать(буфер, 0, 255)
печатать(память.прочитать(буфер, 0))

печатать(память.емкость(область))  // 4096
печатать(память.занято(область))   // 32
печатать(память.длина(буфер))      // 32

память.сбросить(область)          // старый буфер недействителен
печатать(память.действителен(буфер))  // ложь

пусть новый = память.выделить(область, 32)
память.закрыть(область)          // backing storage освобождено
печатать(память.действителен(новый)) // ложь
```

При необходимости большого выравнивания его выбирают *при создании* области:

```kirton
импорт память
пусть область = память.создать(1048576, 4096)
пусть буфер = память.выделить(область, 256, 4096)
```

Сигнатуры функций модуля `память`:

| Функция | Результат |
|---|---|
| `создать(байты[, максимальное_выравнивание])` | Область |
| `выделить(область, байты[, выравнивание])` | Буфер |
| `сбросить(область)` | Истина или ошибка |
| `закрыть(область)` | Истина или ошибка |
| `емкость(область)` | Полезная ёмкость в байтах |
| `занято(область)` | Использованные байты, включая зазоры выравнивания |
| `действителен(буфер)` | Истина/ложь |
| `длина(буфер)` | Длина действительного буфера |
| `записать(буфер, индекс, байт)` | Запись `0..255`, истина или ошибка |
| `прочитать(буфер, индекс)` | Целое `0..255` или ошибка |

Ограничения:

- Размеры и индексы — неотрицательные целые, представимые `int64_t` и `size_t` хоста. Все смещения проверяются на выход за границы.
- Выравнивание — степень двойки. Максимальное выравнивание основы области не более `1048576`; по умолчанию `64`. Величина выравнивания отдельного выделения не может превышать выбранное для области максимальное выравнивание.
- Каждое новое выделение **заполняется нулями**, включая повторно используемые байты после сброса. Это осознанный безопасный режим, стоимость обнуления пропорциональна длине выделения.
- Функции чтения и записи проверяют поколение буфера. Сброс области увеличивает поколение; использование старого буфера возвращает диагностическую ошибку. Закрытие освобождает backing storage немедленно и навсегда инвалидирует все буферы.
- Повторный сброс/закрытие закрытой области, выход за границы, исчерпание ёмкости, некорректные размеры и выравнивание — ошибка выполнения. `действителен` позволяет проверить буфер без остановки.
- Типы `область_памяти` и `буфер` не сериализуются в JSON. Попытка сериализации вызывает диагностическую ошибку, а не неявный `null`.

## 3. Взаимодействие с GC и C API

- `VAL_ARENA` и `VAL_BUFFER` — новые виды `Value`, которые учитываются в куче VM.
- В фазе mark достижимый буфер помечает и родительскую область, даже если переменная с областью была перезаписана. Sweep освобождает неиспользуемые дескрипторы и ещё не закрытые резервирования.
- Возвращённые в C значения *не закрепляются автоматически*. Перед потенциальной сборкой вызывать `vm_value_pin`, после работы — `vm_value_unpin`. Созданные вне VM области отвергаются; передача прямого дескриптора области/буфера в другую VM отвергается на границе `vm_call_by_name` / `vm_value_pin`.
- Ограничение резервирований на VM: `vm_memory_set_arena_limit(vm, байты)`; `vm_memory_arena_bytes(vm)` возвращает текущую суммарную полезную ёмкость открытых областей. При превышении лимита создание новой области не проходит.
- Автоматический GC запускается не только по числу объектов, но и по объёму резервирований **открытых областей**: шаг `16 МиБ` сверх объёма, оставшегося после прошлой сборки. Это эвристика, не строгая квота на всю память VM.
- Нативная память *не предоставляет* доступ к сырым указателям на языке Kirton; `VAL_BUFFER` сейчас представляет проверяемый диапазон байтов.

## 4. Что остаётся вне этого этапа

1. Нет полноценного ручного `malloc/free` с сырыми указателями и блоком `небезопасно`. Это должно появиться только вместе с правилами владения и общим C ABI.
2. Нельзя произвольно размещать обычные `строка`, `список`, `словарь` или объект в арене; пока размещаются только байты. Типизированные массивы (`целое32`, `число64`, структуры) ещё не реализованы.
3. Лимит VM отслеживает только **полезные резервирования арен**; он не является ограничением на всю оперативную память. Не включает накладные расходы выравнивания, метаданные GC, строки, коллекции, BigInt, AST, сторонние библиотеки, GPU-память.
4. Нативные модули и глобальные таблицы всё ещё нуждаются в отдельном аудите владения. Прямые *вложенные* ссылки на значения другой VM в произвольных C-коллекциях пока не проверяются рекурсивно.
5. VM и система памяти не потокобезопасны; нельзя одновременно выполнять её методы из разных потоков.
6. Ошибки модуля `память` пока не всегда привязаны к точной позиции вызова в исходном коде. Обрабатываемые исключения языка ещё не готовы.
7. Дескрипторы буферов по-прежнему являются объектами GC, поэтому большое количество мелких буферов создаёт нагрузку на GC; оптимизации/специализированные стековые представления остаются будущей работой.
8. Windows/MSVC и Win32-графические программы **не проверены** в этом окружении; все прогоны выполнены на Linux/GCC.

## 5. Порядок дальнейшей работы

1. Довести учёт **всей** памяти (не только arena payload), наложить лимиты на VM, покрыть OOM и ошибки API.
2. Ввести типизированные непрерывные массивы и структуры, выделяемые в арене, с проверкой выравнивания и времени жизни.
3. Формализовать передачу/заимствование ссылок между GC, аренами, внешними C-модулями и callback.
4. Реализовать явные нативные дескрипторы/ресурсы и ограниченный `небезопасно`, не нарушая семантику безопасного Kirton.
5. Нагрузочные профили, сравнение GC/арен, оптимизация аллокаций, совместимость MSVC/Windows и конформанс-тесты.
