# Kirton Memory System V2.6 — первый C ABI/FFI для нативных библиотек

**Статус:** экспериментальная реализованная подсистема. Продолжение V2.5. Это *согласованный плагинный C ABI*, а не произвольные вызовы любых экспортов из libc/Vulkan/других DLL. **Windows/MSVC не проверялись**. За пределами C ABI действуют прежние правила GC, арен, нативных ресурсов и borrowing из V2.0–V2.5.

## Что реализовано

- Динамическая загрузка библиотек через `dlopen` (POSIX) или `LoadLibraryW` (Windows, путь UTF-8).
- Экспорт единого символа `kirton_ffi_module_v1` с описанием модуля и сигнатур функций. Версия ABI и размер заголовка проверяются *до* регистрации функций. Метаданные сохраняются пока загружена библиотека.
- Типизированные синхронные функции на `целое64` (точное), `число64`, `логическое`, `текст` и `пусто` как возвращаемый тип. Ограничение: максимум 16 аргументов. Строки передаются как `(const char* bytes, size_t length)`, включая возможный NUL. Возвращаемые строки копируются в память VM *до* возврата управления скрипту.
- Библиотеки живут в конкретной VM; повторные названия модулей отклоняются. После успешного уничтожения VM динамические библиотеки выгружаются.
- Ошибки неподходящего типа/количества аргументов, несовместимой версии ABI и неправильного результата функции приводят к диагностике. Функции возвращают 1 (успех) или 0 (ошибка).
- FFI отключён по умолчанию. Пользователь CLI явно включает его через `--allow-ffi`, C-хост — `vm_ffi_set_enabled(vm, 1)`.
- Запуск GC и уничтожение VM во время FFI-вызова через публичные VM API блокируются. Поддерживается только один поток и синхронный вызов.

## Как использовать в Kirton

```text
импорт внешний
внешний.загрузить("./kirton_ffi_v2_plugin.so")
пусть ответ = внешний.вызвать("арифметика", "сложить", 9007199254740993, 7)
печатать(ответ)
```

Запуск (Linux): `./kirton --allow-ffi example.kir`. На Windows расширение библиотеки — `.dll`.

Это исполнение **произвольного доверенного нативного кода внутри процесса**: библиотека скомпилирована на C и может делать всё, что позволяет ОС процессу. Флаг `--allow-ffi` не делает чужие библиотеки безопасными. Не загружайте недоверенные модули.

## C ABI

Заголовок `include/kirton/ffi.h` не содержит `Value`, `VM` или указатели на внутренние объекты. Он объявляет `KirFfiValue`, `KirFfiFunctionV1`, `KirFfiModuleV1` и `KirFfiInvoke`.

```c
#include "kirton/ffi.h"
static int add(uint32_t argc, const KirFfiValue* a, KirFfiValue* out) {
    if (argc != 2) return 0;
    out->type = KIR_FFI_I64;
    out->data.i64 = a[0].data.i64 + a[1].data.i64;
    return 1;
}
static const uint32_t args[] = { KIR_FFI_I64, KIR_FFI_I64 };
static const KirFfiFunctionV1 functions[] = {
    {"сложить", 2, args, KIR_FFI_I64, add}
};
static const KirFfiModuleV1 module = {
    KIR_FFI_ABI_V1, sizeof(KirFfiModuleV1), "арифметика", 1, functions
};
/* На Windows: __declspec(dllexport) и extern "C" для C++. */
const KirFfiModuleV1* kirton_ffi_module_v1(void) { return &module; }
```

Для демонстрации уже включена настоящая библиотека `tests/ffi_v2_plugin.c`, собираемая CMake в `kirton_ffi_v2_plugin.so` / `.dll`. C ABI завязан на архитектуру и используемый C ABI платформы: нельзя смешивать 32- и 64-битные модули, произвольные calling conventions или несовместимые компиляторные настройки.

## API хоста

В `include/kirton/eval.h`:

```c
int vm_ffi_set_enabled(VM* vm, int enabled);
int vm_ffi_load(VM* vm, const char* path_utf8);
int vm_ffi_call(VM* vm, const char* module, const char* name,
                int argc, const Value* argv, Value* result);
const char* vm_ffi_last_error(const VM* vm);
```

Библиотека не владеет строками или массивами аргументов, не имеет права сохранять адрес полученного текста, аргументов или массива результатов после возврата `invoke`. Для результата TEXT возвращаемые байты должны быть валидны до завершения callback: Kirton копирует их сразу. C API `Value` вне VM сохраняет прежние правила закрепления через `vm_value_pin()`.

## Что ещё нельзя считать реализованным

- Нет libffi и вызова произвольных C-сигнатур. Нельзя сделать `внешний.вызвать("vulkan", "vkCreateDevice", ...)` без нативного адаптера.
- Нет raw pointer, структур по значению, varargs, прямого доступа к GPU, асинхронных callback и передачи GC-объектов в native код.
- Нет изоляции или песочницы для DLL/SO. Вредоносный или ошибочный C-код может повредить память независимо от проверок Kirton.
- Нет многопоточной синхронизации и lifetime-модели для GPU/DMA или долгоживущих нативных указателей.
- Существующий ABI V1 ещё экспериментальный: до стабильного Kirton 1.0 необходимо проверить Windows/MSVC и реальную стороннюю библиотеку, измерить накладные расходы, опубликовать правила совместимости.

## Тесты

`tests/ffi_v2_api.c`, `tests/ffi_v2_plugin.c`, `tests/ffi_v2_bad_abi.c`, `tests/ffi_v2_vm.kir`, `tests/ffi_v2_disabled.kir` и CMake-генерируемая CLI-программа проверяют: exact i64 больше 2^53, числа64, логические значения, строки с NUL, void, ошибку callback, неправильный тип результата, чужую/отсутствующую функцию, число аргументов, запрет без opt-in, ошибку загрузки, несовместимую версию ABI, повторную загрузку, независимую регистрацию в VM, GC во время удержания результата, запуск из скрипта и CLI.

Проверки разработчика: Release **61/61**, ASan+UBSan+LeakSanitizer **61/61** (Linux GCC). Это не формальная гарантия корректности или производительности.
