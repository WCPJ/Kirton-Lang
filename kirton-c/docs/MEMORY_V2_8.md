# Kirton Memory System V2.8 — замыкание базового native lifetime

**Статус:** реализованный экспериментальный слой поверх V2.6. Исходный интерпретатор, GC, арены, типизированные массивы, записи, borrowing, native resources и FFI V1 сохранены. Новые механизмы: проверяемая передача записей и ресурсов через плагинный **FFI ABI V2**, а также явная аренда (`lease`) ресурса на время долгих нативных операций. **Linux/GCC, Windows/MSVC и Windows AddressSanitizer проверены; настоящие Vulkan/GPU/асинхронные драйверы не проверялись.**

## Что появилось

1. **Плагинный ABI V2**, экспорт `kirton_ffi_module_v2` в дополнение к прежнему V1. Старые `kirton_ffi_module_v1` продолжают работать без перекомпиляции; имена модулей уникальны в пределах VM независимо от версии ABI. Если библиотека экспортирует V2, проверка V2 обязательна: при неверной версии нельзя молча переключиться на V1.
2. **Передача типизированных записей:** в C передаётся копия байтов записи, а не указатель на память арены. До вызова проверяются число, порядок, имена, типы, смещения, выравнивание и `sizeof` полей. Разрешены только фиксированные скалярные поля (`байт`, `целое32`, `целое64`, `число64`), без GC-ссылок и указателей. Изменение копии не меняет запись Kirton. Функция C может вернуть собственную запись; Kirton создаёт для неё управляемую GC-схему, арену и запись с копированием. Неконечные `число64` в результате отвергаются.
3. **Непрозрачные ресурсы:** плагин получает временный числовой токен, а не адрес VM или `Value`. На время синхронного вызова `host->visit_resource(...)` позволяет обратиться к проверенному ресурсу с указанным `type_tag`, удерживая ресурс от GC/close. Можно вернуть **существующий** входной дескриптор, но нельзя создать новую произвольную ссылку или вернуть придуманный токен.
4. **Длительные native lease:** C-хост может получить `vm_native_resource_lease_begin(...)`, передать внешний handle нативному API через синхронный callback и не выпускать lease, пока асинхронная операция реально не завершится. GC сохраняет объект, `close` отклоняется, `vm_try_free()` отклоняется. После `vm_native_resource_lease_release()` ресурсы снова обслуживаются обычным GC/close. Несколько lease для одного ресурса возможны; закрыть ресурс можно лишь после освобождения всех.
5. **Порядок завершения VM:** загруженные native библиотеки теперь остаются до завершения финализаторов ресурсов, чтобы функция освобождения из `.so`/`.dll` не оказалась выгруженной раньше дескриптора.

## Синтаксис Kirton

Новые возможности FFI V2 используют прежний вид вызова:

```text
импорт память
импорт внешний
внешний.загрузить("./kirton_ffi_v3_plugin.so")

пусть схема = память.структура("здоровье", "целое32", "идентификатор", "целое64", "скорость", "число64")
пусть область = память.создать(4096)
пусть игрок = память.запись(область, схема)
игрок.здоровье = 42
игрок.идентификатор = 9007199254740993
игрок.скорость = 2.5

пусть ответ = внешний.вызвать("структуры", "проверить", игрок)
печатать(ответ)
```

Запуск: `kirton --allow-ffi программа.kir`. Без флага загрузка нативных библиотек не разрешена. На Windows загрузите совместимую DLL вместо `.so`.

## FFI V2 — правила C ABI

Заголовок: `include/kirton/ffi.h`. Новые типы: `KirFfiModuleV2`, `KirFfiFunctionV2`, `KirFfiParamV2`, `KirFfiRecordSchemaV2`, `KirFfiValueV2`, `KirFfiHostV2`.

- Входные типы: I64, F64, BOOL, TEXT, RECORD, RESOURCE. Возвращаемые дополнительно VOID. Ограничение: 16 аргументов.
- Scalar F64 arguments accept IEEE-754 NaN and infinities. FFI V2 rejects non-finite scalar F64 results and non-finite F64 fields in returned records. FFI V1 preserves its legacy behavior and passes non-finite F64 values in both directions.
- Для RECORD укажите полную C-совместимую схему (`offsetof`, `sizeof`, `_Alignof`) с порядком полей. Совместимость байтового расположения **платформенная**, а не wire format; передача между машинами с иной архитектурой не гарантируется. На входе все поля схемы сверяются с записью Kirton; снимок принадлежит вызову и не сохраняется плагином.
- Возвращённые RECORD/TEXT копируются в память VM. Адрес возврата должен оставаться действительным до завершения `invoke()`.
- Для RESOURCE укажите `resource_type` и вызывайте `host->visit_resource(host, token, type_tag, visitor, user_data)` только во время `invoke()`. Визитор синхронный. Токен **не** является глобальным ID: не храните его и `host` после выхода из функции.
- В качестве RESOURCE результата допускается только токен уже переданного ресурса с совпадающим типом. Захват владения новым внешним C handle из плагина не реализован.
- Возврат `0` из нативной функции обозначает ошибку. Произвольный C-код по-прежнему полностью доверенный: ошибка указателя может повредить процесс. Флаг `--allow-ffi` не является песочницей.
- ABI V2 намеренно выделен новым символом: нельзя «переназвать» существующую V1-функцию на V2 без обновления структуры сигнатур и callback.

Реальный пример модуля: `tests/ffi_v3_plugin.c`; примеры вызова и проверки: `tests/ffi_v3_api.c`, `tests/ffi_v3_vm.kir`, CMake-генерируемый `ffi_v3_cli.kir`.

## Длительные native leases (C API)

```c
KirNativeResourceLease* lease = vm_native_resource_lease_begin(vm, resource, "gpu-buffer");
if (!lease) { /* неверный/закрытый/чужой ресурс */ }
else {
    /* В callback: вызвать внешнее API, которое начинает работу с handle.
       НЕЛЬЗЯ использовать handle за пределами контракта ОС/драйвера. */
    vm_native_resource_lease_visit(vm, lease, submit_native_operation, user_data);

    /* ... дождаться настоящего завершения внешнего I/O/GPU/DMA ... */
    vm_native_resource_lease_release(vm, lease);
}
```

- `begin()` копирует метку типа, создаёт GC-pin, увеличивает счётчик защиты от закрытия. Чужие VM и неверные типы отклоняются.
- `lease_visit()` временно выдаёт C-адрес внешнего ресурса внутри callback; callback может лишь *запустить* долгую нативную операцию. Само заимствование адреса не превращает внешний API в безопасный.
- `release()` вызывается **только после подтверждённого завершения** операции. Если освободить lease раньше, GC/close смогут уничтожить ресурс, пока внешняя операция ещё работает.
- `vm_try_free()` возвращает `0`, пока остаётся хотя бы одна lease. `vm_free()` также откажется завершать VM; хост обязан снять leases.
- Повторный release, release из чужой VM, закрытие ресурса при lease, release из действующего visit callback — отклоняются.
- **Однопоточная модель:** все обращения к VM и lease должны идти из одного управляющего потока. Lease можно держать между вызовами, пока внешнее устройство работает асинхронно; нельзя одновременно трогать Kirton VM из других потоков.
- Это API хоста, а не открытая команда для скрипта. Автоматического отслеживания GPU-fence / completion event нет.

## Проверки

Команды Linux:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
```

ASan + UBSan + LeakSanitizer:

```sh
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON \
  -DCMAKE_C_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer -g -O1' \
  -DCMAKE_EXE_LINKER_FLAGS='-fsanitize=address,undefined' \
  -DCMAKE_SHARED_LINKER_FLAGS='-fsanitize=address,undefined'
cmake --build build-asan -j
ASAN_OPTIONS='detect_leaks=1:halt_on_error=1' UBSAN_OPTIONS='halt_on_error=1' \
  ctest --test-dir build-asan --output-on-failure -j1
```

Исторический Linux/GCC прогон прошёл **64/64 Release и 64/64 ASan/UBSan/LSan** на прежнем состоянии тестов; текущий Linux-прогон не подтверждён. В текущем Windows x64/MSVC окружении Debug, Release и AddressSanitizer прошли **125/125 CTest каждый**. Новые проверки: совпадение схемы с `offsetof` C-структуры, изолированная копия записи, точное i64 больше 2^53, возврат GC-managed записи, отклонение NaN в поле, неверная схема, чужой дескриптор, поддельный токен, закрытый ресурс, GC и повторное закрытие, скриптовый FFI V2, `lease`/GC/close/VM lifetime, раннее освобождение lease внутри callback, несовместимый ABI, совместимость FFI V1.

## Аудит: что ещё остаётся нерешённым

**V2.8 не означает полной доказанной безопасности памяти всего Kirton и не является финальным release 1.0.**

- **Windows/MSVC проверен сборкой, CTest и AddressSanitizer.** Отдельно остаются другие версии компилятора/SDK и ручные сценарии графических нативных модулей.
- **Старые нативные модули** (`mod_window`, `mod_gl`, `mod_d3d11`, `mod_sound`, `mod_bitmap` и др.) имеют собственное управление внешними объектами, не обязаны использовать новый `VAL_NATIVE_RESOURCE`. Нужен отдельный аудит освобождения и VM-изоляции этих модулей.
- **Нет потокобезопасности VM или GC.** Нативный плагин может вести собственные потоки, но не должен вызывать VM API из них.
- **FFI не универсальная libffi:** arbitrary C signatures, varargs, функции Vulkan напрямую, C++ ABI, callbacks из скрипта, долгоживущие сырые указатели не реализованы. Для Vulkan требуется совместимый нативный адаптер.
- **Ограничение нативного кода:** доверенная DLL/SO может сама хранить сырой адрес после callback, неправильно освобождать ресурсы или запускать async работу после lease_release — такие ошибки нельзя исключить проверками VM.
- **Память VM пока не полностью подсчитывается в байтах:** лимит резервов арен есть, но суммарное потребление всех GC-объектов, модулей и сторонних библиотек не охватывается одним счётчиком.
- **Протокол владения для C-кода обязателен:** `Value`, удерживаемый вне VM между сборками GC, требует `vm_value_pin`; использующий старый указатель C-код несёт ответственность за UAF. Автоматическая защита произвольных сырых C-указателей недостижима.
- **Не измерена длительность GC на промышленных нагрузках** и не оптимизирована модель пауз. Нужны нагрузочные профили реальных приложений.

**Рекомендация по порядку работ:** считать Memory System V2.8 работоспособной экспериментальной основой, временно остановить расширение её API и переключиться на правила функций, модулей, обработку ошибок и спецификацию языка. Вернуться к памяти перед стабильным 1.0 для Windows-тестов и аудита существующих нативных модулей.
