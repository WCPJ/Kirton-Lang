# Kirton Memory System V2.2 — записи с фиксированной раскладкой

Дата: 2026-11-03. Экспериментальный этап, совместимый с Memory V2.1, но **не спецификация Kirton 1.0 и не готовый FFI**.

## Результат

В модуле `память` появились неизменяемые схемы структур и размещённые в аренах записи. Поля имеют имена на русском или другом UTF-8, но **их значения — только числовые скаляры**, без VM-ссылок. Код может читать и писать поля, не получая сырой указатель. Структуры используют естественное выравнивание C для текущей платформы, включая промежуточные и конечные байты выравнивания.

```kirton
импорт память

пусть точка = память.структура(
    "x", "число64",
    "y", "число64",
    "номер", "целое64"
)

пусть область = память.создать(1024)
пусть позиция = память.запись(область, точка)
позиция.x = 10.5
позиция["y"] = -1.25
позиция.номер = 9007199254740993

печатать(позиция.x)
печатать(память.размер_структуры(точка))
печатать(память.смещение_поля(точка, "номер"))

память.сбросить(область)
печатать(память.действительна_запись(позиция))  // ложь
```

## API

| Функция | Назначение |
|---|---|
| `память.структура(имя1, тип1, ...)` | создать неизменяемую схему; 1–256 полей |
| `память.запись(область, схема)` | разместить нулевую запись в арене |
| `память.размер_структуры(схема)` | размер с учётом конечного выравнивания, в байтах |
| `память.выравнивание_структуры(схема)` | требуемое выравнивание объекта |
| `память.смещение_поля(схема, имя)` | смещение поля от начала записи, в байтах |
| `память.тип_поля(схема, имя)` | строковое название типа |
| `память.действительна_запись(запись)` | не была ли арена закрыта/сброшена |
| `память.взять_поле(запись, имя)` | чтение поля |
| `память.положить_поле(запись, имя, значение)` | запись значения с проверкой типа/диапазона |

Дополнительно поддерживаются `запись.поле`, `запись.поле = число`, `запись["поле"]`, `запись["поле"] = число`.

Типы: `байт` (uint8_t), `целое32` (int32_t), `целое64` (int64_t), `число64` (double). Числа `целое64` сохраняются **точно**, в том числе за пределами точности IEEE 754 double. Для `число64` допускаются только конечные значения. Для целочисленных полей требуется точное целое, соответствующее диапазону типа. Память выделенной записи обнуляется.

Пустые/повторяющиеся имена и NUL внутри имени отвергаются; имя ограничено 255 байтами. Тип и количество полей проверяются. Доступ к отсутствующему полю — ошибка выполнения, а не `пусто`.

## Гарантии текущей модели

1. Схема создаётся как объект в куче VM и не может быть изменена после создания. Строки имён полей копируются в схему.
2. Запись представляет собой GC-дескриптор для диапазона байтов в арене. При создании выполняются проверки вместимости, выравнивания и переполнения размеров.
3. Дескриптор записи удерживает **и арену, и схему** достижимыми во время сборки мусора. Вложенные списки и словари могут содержать записи.
4. `сбросить`/`закрыть` немедленно инвалидируют старые записи (generation check), но не обязаны освобождать их дескрипторы до следующей сборки мусора.
5. При попытке передать чужую запись/схему через `vm_value_pin` или `vm_call_by_name` выполняется проверка владельца. Вложенные и циклические контейнеры обходятся рекурсивно по графу со множеством посещённых объектов.
6. `json.написать` отвергает записи и схемы: передавать нативную раскладку через JSON без явного преобразования нельзя.
7. **Содержимое арены не сканируется GC на ссылки VM**. Поэтому в полях разрешены только скаляры, а не строки/списки/словари/другие записи по ссылке.

## C-совместимость и ограничения

Для типов с фиксированной шириной используется `sizeof` и `_Alignof` C11 данной платформы, а смещения вычисляются с естественными отступами, как у обычной C-структуры из этих полей. В тесте `memory_v2_record_api.c` размер и смещения сверяются с настоящей `struct` через `sizeof`, `offsetof` и `_Alignof`.

**Это не полноценный C ABI.** Пока отсутствуют FFI-вызовы, сырые указатели, union, битовые поля, вложенные структуры, packed-layout, параметрические целевые ABI, экспорт адресов, callback, управление владением для внешнего C-кода. Байтовый порядок платформенный, схемы не предназначены для сети или дисковых форматов без отдельного кодека. Точность раскладки для иных архитектур/компиляторов не проверялась.

**Важно для C API.** При выполнении внутри VM проверяется принадлежность объектов текущей куче. Если нативный код обращается к `v_record_get`/`v_record_set` **вне** активного контекста VM, он обязан сохранять Value с помощью `vm_value_pin` и не использовать его после `unpin`/`vm_free` (аналогично ранее существовавшему API массивов). Использование произвольного или просроченного C-указателя C API пока не может быть сделано безопасным. Это важная граница для будущего FFI и контекстного C API.

При обращении к полю по строке выполняется линейный поиск по описанию структуры (`O(число_полей)`). Для горячих циклов в будущем потребуется связывание полей во время компиляции/байткодной компиляции с проверкой идентичности схемы.

## Проверки

Вместе с прежними тестами V2.1: **54/54 Release** и **54/54 с ASan/UBSan и включённым LeakSanitizer** на Linux/GCC (локальная среда).

Новые тесты включают:

- реальное чтение и запись через точку/индекс, псевдонимы одной записи и отдельные экземпляры;
- нулевые значения и точность int64, проверку диапазона uint8/int32, NaN/Infinity;
- отказы для повторных имён, неверных типов, отсутствующего поля, недостаточной ёмкости, JSON, stale-записей;
- удержание схемы и арены GC при наличии только одного достижимого дескриптора записи;
- попытки передать чужую запись между VM напрямую и внутри циклических контейнеров;
- C-размеры/смещения и нагрузку 120 × 15 000 = **1 800 000 созданий дескрипторов записей** со сбросом арены и сборкой GC.

Запуск:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Санитайзеры (GCC/Clang):

```sh
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer -g -O1' \
  -DCMAKE_EXE_LINKER_FLAGS='-fsanitize=address,undefined'
cmake --build build-asan -j
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 UBSAN_OPTIONS=halt_on_error=1 \
  ctest --test-dir build-asan --output-on-failure
```

Windows/MSVC не проверялись; результаты тестов не являются формальным доказательством отсутствия дефектов.

## Следующие этапы

1. Единый C API с явным контекстом VM, проверкой времени жизни дескрипторов и договором владения.
2. Ограниченные представления срезов/массивов структур, не допускающие скрытых ссылок на GC.
3. Разделение безопасных и `небезопасно` операций; правила заимствования памяти между GC и ручной ареной.
4. Явный FFI с привязкой к платформенному ABI, только после аудита памяти и Windows/MSVC.
5. Система исключений, чтобы ошибку использования невалидной записи можно было обработать в самом Kirton.
